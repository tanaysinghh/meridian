# Deploying Meridian on Render

Step-by-step walkthrough for a first-time Render deploy of Meridian.

> **Status.** Deployed and working. All four services are live on Render
> (URLs in [§ 3](#3--verify)), running against Render's own managed Postgres
> — the `DATABASE_URL` that `render.yaml` wires from the `meridian-db`
> block. Sign-in, the dashboard and GitHub OAuth all work end to end
> against seeded demo data. What is *not* exercised in production is live
> webhook ingestion: the GitHub App exists but is not installed on a real
> repository, so no deliveries arrive. See
> [§ 5](#5--what-to-watch-on-free-tier) for the free-tier caveats that
> still apply.

Meridian ships four things:
- **meridian-db**  — managed Postgres 15 (private).
- **meridian-ml**  — FastAPI risk scorer (public web service, gated by a
  shared-secret `X-Internal-Secret` header — Render free tier does not
  support private services, so we authenticate at the app layer instead).
- **meridian-api** — Java 21 / Spring Boot backend, built from a Dockerfile
  (public). REST plus STOMP-over-WebSocket.
- **meridian-web** — Vite React static site (public).

The Blueprint file `render.yaml` in the repo root defines all four so you can
provision them in one go.

---

## 0 · Prereqs

- Render account (free tier is fine to try; upgrade `api`/`db` to Starter for
  anything real — free web services spin down after inactivity and will drop
  your realtime WebSocket connections).
- The Meridian repo pushed to a GitHub org Render can read.
- (Optional but recommended) A GitHub App created for Meridian ahead of time,
  so you have `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` / `GITHUB_APP_ID`
  ready to paste. If you skip this, GitHub sign-in will return a clean 503 —
  the rest of the app still works via email/password.

---

## 1 · Apply the Blueprint

1. Render dashboard → **New** → **Blueprint**.
2. Select the Meridian repo. Render reads `render.yaml` and shows you the
   four resources it's about to create.
3. It will prompt you to fill in every env var marked `sync: false`. **Leave
   the ones you don't know yet blank** — you'll fill them in after step 3.
   The ones you definitely need up front:
   - `ADMIN_EMAIL` and `ADMIN_PASSWORD` (used to bootstrap the first admin).
4. Click **Apply**. Render provisions the DB, then builds ml + api + web in
   parallel. Expect ~5–8 minutes on the first go.

Note the URLs Render assigns. **When the plain name is already taken, Render
appends a random suffix**, so do not assume they match the service names — read
them off each service's page. The current live deployment is:

| service | URL |
|---------|-----|
| `meridian-api` | `https://meridian-api-il0f.onrender.com` |
| `meridian-web` | `https://meridian-web-1pi4.onrender.com` |
| `meridian-ml`  | `https://meridian-ml.onrender.com` |

Every value below uses these. A fresh apply will get different suffixes;
substitute yours throughout.

The ml service *does* have a public URL on the free tier (Render doesn't
offer private services there), but `/score` requires an `X-Internal-Secret`
header that matches `ML_INTERNAL_SECRET`. Render auto-generates that secret
on the ml service and the api reads the same value via a `fromService`
binding, so nothing needs to be copied by hand. Only `/health/live` and
`/health/ready` are open (Render needs to hit them to mark the service
healthy).

## 2 · Fill in the "you supply" env vars

Now that you know the URLs, go back and set the remaining vars.

### On `meridian-api` (Environment tab)

| Var | Value |
|---|---|
| `WEB_ORIGIN` | `https://meridian-web-1pi4.onrender.com` |
| `ALLOWED_ORIGINS` | `https://meridian-web-1pi4.onrender.com` (comma-separated if multiple) |
| `ML_SERVICE_URL` | `https://meridian-ml.onrender.com` |
| `GITHUB_CLIENT_ID` | from your GitHub App |
| `GITHUB_CLIENT_SECRET` | from your GitHub App |
| `GITHUB_OAUTH_CALLBACK` | `https://meridian-api-il0f.onrender.com/auth/github/callback` |
| `GITHUB_APP_ID` | from your GitHub App |

> **None of these are optional.** They are `sync: false` in the Blueprint, which
> means Render *prompts* for them rather than defaulting them — and if you skip
> the prompt the service still starts, falling through to values meant for local
> development. On the first rollout all of them were left unset, and the result
> was four healthy-looking services over a product that did not work at all.
> See `DECISIONS.md § Deployment pitfalls`.

`GITHUB_WEBHOOK_SECRET`, `JWT_SECRET`, and `ML_INTERNAL_SECRET` were
generated by Render — leave them alone. The ml-side value of
`ML_INTERNAL_SECRET` is auto-bound to the api via `fromService`, so both
services always see the same secret. Copy the generated
`GITHUB_WEBHOOK_SECRET` into your GitHub App's webhook config
(Settings → Webhooks → Secret) so signatures match.

Save → Render redeploys the api service automatically.

### On `meridian-web` (Environment tab)

| Var | Value |
|---|---|
| `VITE_API_BASE` | `https://meridian-api-il0f.onrender.com` |

`VITE_API_BASE` is a **build-time** var, so Render triggers a fresh build
when you save it. Wait for the build to finish before testing.

## 3 · Verify

- Visit the web URL. The landing page should render on the new dark palette
  with the brand blue (#035BD6).
- Hit `https://meridian-api-il0f.onrender.com/health/ready` — should return
  `{"ok": true, "status": "ready"}`. If it 503s, the api can't reach the DB
  (check the `DATABASE_URL` binding on the api's env vars).
- Sign in with the `ADMIN_EMAIL` / `ADMIN_PASSWORD` you set. If it works, the
  first-run migration did what it was supposed to.

### Bootstrap the admin user (one-off)

Flyway migrates the schema automatically during startup, so there is no
migration step to run. Creating the first org and admin user is a separate,
explicit action — ordinary deploys never touch user records.

Set `ADMIN_EMAIL` and `ADMIN_PASSWORD` (12+ characters) on the api service,
then from the Render **Shell**:

```bash
java -jar /app/meridian-api.jar --seed
```

It is idempotent: re-running updates the admin's password and name rather
than creating a duplicate. Under the prod profile it refuses to run without
both variables set — it will not invent a default administrator.

Clear `ADMIN_PASSWORD` from the service env once the account exists.

### Loading the demo dataset

`--seed-demo` additionally loads the sample Acme dataset — four repos, eight
pull requests across the risk tiers, escalation rules, an incident linked to
the PR that caused it, and the file hotness / ownership tables behind reviewer
suggestions. It attaches everything to the bootstrapped org, so the admin
account and the data always share a tenant.

Without shell access, drive it from the Environment tab instead:

```
MERIDIAN_SEED_DEMO=true
FORCE_DEMO_SEED=yes
```

Save, let the service redeploy, confirm the dashboard is populated, then
**remove both variables**. They are not inert: the seeder clears the org's
existing repos, PRs, rules and incidents before re-inserting, so leaving them
set means every future restart wipes whatever real data has accumulated.

`FORCE_DEMO_SEED` is required under the prod profile — the seeder refuses
otherwise, because demo rows are hard to distinguish from real ones later.

## 4 · Wire up webhooks

In your GitHub App:
- **Webhook URL**: `https://meridian-api-il0f.onrender.com/webhooks/github`
- **Webhook secret**: the value of `GITHUB_WEBHOOK_SECRET` from the api env.
- Subscribe to exactly two events: **Pull request** and **Pull request
  review**. `GithubWebhookController` handles only these; anything else is
  acknowledged and dropped, so subscribing more just adds ignored traffic.
- **Permissions** — the minimum the code actually uses:
  - Repository → **Metadata**: Read-only (mandatory, auto-selected)
  - Repository → **Pull requests**: Read-only (the only repo data read, and
    what gates the two events above)
  - Account → **Email addresses**: Read-only (OAuth login calls
    `/user/emails`; without this, sign-in fails with
    `github_no_verified_email`)

  Contents, Checks, Issues and Actions are deliberately *not* requested —
  nothing in the codebase reads them.

Install the app on a test repo. Open a PR — the dashboard should light up
within a few seconds (realtime push) with a scored PR row.

## 5 · What to watch on free tier

- **One free Postgres per account.** Render's free tier caps you at a
  single free Postgres database *per account*. If your account already has
  one attached to another project, the Blueprint apply will fail at the
  `databases.meridian-db` step with a "plan limit" error. Three ways to
  fix, cheapest first:
    1. **Drop the existing free DB** (if the other project no longer needs
       it), then re-apply the Blueprint.
    2. **Upgrade `meridian-db` to a paid plan** in `render.yaml`
       (`plan: starter` on the `databases` block) — this bypasses the free
       cap and gets you daily backups.
    3. **Apply the Blueprint from a separate Render workspace** — a fresh
       workspace has its own free-tier quota.
- **Spin-down**: free web services sleep after 15 minutes of no traffic.
  When the api sleeps, the WebSocket drops and the first request after a
  sleep takes ~30s. `meridian-ml` is also a free web service (free tier
  has no `pserv`), so it sleeps too and the first scoring request after
  idle will be slow. The api's `scorePR` already falls back to a
  rule-only score if the ml call fails or times out, so webhook
  ingestion doesn't stall.
- **DB retention**: free Postgres expires after 90 days and is deleted.
  Move to a paid plan before you care about the data.
- **Region locking**: keep all four resources in the same region so the
  api → ml round-trip stays on Render's backbone rather than the public
  internet.

## 6 · Custom domains (optional)

If you want `app.yourcompany.com` instead of the `.onrender.com` URLs:

1. Add a custom domain on `meridian-web` and `meridian-api` in the Render
   dashboard. Follow the DNS instructions Render gives you.
2. Update `WEB_ORIGIN`, `ALLOWED_ORIGINS`, `VITE_API_BASE`, and
   `GITHUB_OAUTH_CALLBACK` to the new hostnames.
3. Custom domains under one apex make this *simpler* than the default
   `.onrender.com` setup. `app.co` and `api.app.co` are the same site, so
   you can set `COOKIE_SAME_SITE=Lax` instead of the prod default `None` and the auth cookie
   stops being a third-party cookie. See the split-origin note in
   `DECISIONS.md` for why the `.onrender.com` hostnames force `None`.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Web loads but every API call is CORS-blocked | `ALLOWED_ORIGINS` on api doesn't include the exact web origin (scheme + host, no path) |
| GitHub sign-in button 503s | GitHub App creds not set on api — this is intentional (no silent fallback). Set them or ignore. |
| `/health/ready` returns `db_unreachable` | `DATABASE_URL` binding broken, or DB is still provisioning. Redeploy api after the DB shows "Available." |
| Realtime WebSocket won't connect in prod | `VITE_API_BASE` wasn't set at web build time. Change it in the web service env and trigger a rebuild. |
| Webhook returns 401 | `GITHUB_WEBHOOK_SECRET` in the api env doesn't match the value in your GitHub App's webhook config. |
| Login POST returns 403 across two different hostnames | `COOKIE_SAME_SITE` was overridden away from the prod default of `None`, or the web build predates the `X-CSRF-Token` header read. Both halves are needed — see the split-origin note in `DECISIONS.md`. |
| Signed in, but every subsequent call is 401 | The auth cookie was set without `SameSite=None; Secure`, so the browser drops it on cross-site requests. The prod profile sets both already; check nothing overrides `COOKIE_SAME_SITE`. |
| ML service returns 503 on first call after idle | Free tier cold start. Upgrade `meridian-ml` to Starter to keep it warm. |
