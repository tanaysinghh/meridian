# Deploying Meridian on Render

Step-by-step walkthrough for a first-time Render deploy of Meridian.

Meridian ships four things:
- **meridian-db**  — managed Postgres 16 (private).
- **meridian-ml**  — FastAPI risk scorer (public web service, gated by a
  shared-secret `X-Internal-Secret` header — Render free tier does not
  support private services, so we authenticate at the app layer instead).
- **meridian-api** — Node/Express + Socket.IO backend (public).
- **meridian-web** — Vite React static site (public).

The Blueprint file `render.yaml` in the repo root defines all four so you can
provision them in one go.

---

## 0 · Prereqs

- Render account (free tier is fine to try; upgrade `api`/`db` to Starter for
  anything real — free web services spin down after inactivity and will drop
  your Socket.IO connections).
- The Meridian repo pushed to a GitHub org Render can read.
- (Optional but recommended) A GitHub App created for Meridian ahead of time,
  so you have `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` / `GITHUB_APP_ID`
  ready to paste. If you skip this, GitHub sign-in will return a clean 503 —
  the rest of the app still works via email/password.

---

## 1 · Apply the Blueprint

1. Render dashboard → **New** → **Blueprint**.
2. Select the Meridian repo. Render reads `render.yaml` and shows you the
   four resources it's about to create.
3. It will prompt you to fill in every env var marked `sync: false`. **Leave
   the ones you don't know yet blank** — you'll fill them in after step 3.
   The ones you definitely need up front:
   - `ADMIN_EMAIL` and `ADMIN_PASSWORD` (used to bootstrap the first admin).
4. Click **Apply**. Render provisions the DB, then builds ml + api + web in
   parallel. Expect ~5–8 minutes on the first go.

Note the URLs Render assigns — they're unique per account, typically:
- `https://meridian-api.onrender.com`
- `https://meridian-web.onrender.com`
- `https://meridian-ml.onrender.com`

The ml service *does* have a public URL on the free tier (Render doesn't
offer private services there), but `/score` requires an `X-Internal-Secret`
header that matches `ML_INTERNAL_SECRET`. Render auto-generates that secret
on the ml service and the api reads the same value via a `fromService`
binding, so nothing needs to be copied by hand. Only `/health/live` and
`/health/ready` are open (Render needs to hit them to mark the service
healthy).

---

## 2 · Fill in the "you supply" env vars

Now that you know the URLs, go back and set the remaining vars.

### On `meridian-api` (Environment tab)

| Var | Value |
|---|---|
| `WEB_ORIGIN` | `https://meridian-web.onrender.com` |
| `ALLOWED_ORIGINS` | `https://meridian-web.onrender.com` (comma-separated if multiple) |
| `ML_SERVICE_URL` | `https://meridian-ml.onrender.com` (the URL Render assigned the ml service) |
| `GITHUB_CLIENT_ID` | from your GitHub App |
| `GITHUB_CLIENT_SECRET` | from your GitHub App |
| `GITHUB_OAUTH_CALLBACK` | `https://meridian-api.onrender.com/auth/github/callback` |
| `GITHUB_APP_ID` | from your GitHub App |

`GITHUB_WEBHOOK_SECRET`, `JWT_SECRET`, `SESSION_SECRET`, and
`ML_INTERNAL_SECRET` were generated by Render — leave them alone. The
ml-side value of `ML_INTERNAL_SECRET` is auto-bound to the api via
`fromService`, so both services always see the same secret. Copy the generated `GITHUB_WEBHOOK_SECRET` into your GitHub
App's webhook config (Settings → Webhooks → Secret) so signatures match.

Save → Render redeploys the api service automatically.

### On `meridian-web` (Environment tab)

| Var | Value |
|---|---|
| `VITE_API_BASE` | `https://meridian-api.onrender.com` |

`VITE_API_BASE` is a **build-time** var, so Render triggers a fresh build
when you save it. Wait for the build to finish before testing.

---

## 3 · Verify

- Visit the web URL. The landing page should render on the new dark palette
  with the brand blue (#035BD6).
- Hit `https://meridian-api.onrender.com/health/ready` — should return
  `{"ok": true, "status": "ready"}`. If it 503s, the api can't reach the DB
  (check the `DATABASE_URL` binding on the api's env vars).
- Sign in with the `ADMIN_EMAIL` / `ADMIN_PASSWORD` you set. If it works, the
  first-run migrate + seed did what it was supposed to.

### Manual seed (only if needed)

The api's start command runs migrations automatically. Seeding runs on first
boot too, but if you ever need to re-seed the admin or drop demo data, use
the Render **Shell** on the api service:

```bash
# Re-seed admin only
node src/db/seed.js

# Seed demo/Acme dataset (refuses without the explicit env flag in prod)
FORCE_DEMO_SEED=yes node src/db/seed.js --demo
```

`db:migrate` alone is idempotent (the schema uses `CREATE ... IF NOT EXISTS`
throughout), so re-runs are safe.

---

## 4 · Wire up webhooks

In your GitHub App:
- **Webhook URL**: `https://meridian-api.onrender.com/webhooks/github`
- **Webhook secret**: the value of `GITHUB_WEBHOOK_SECRET` from the api env.
- Subscribe to `pull_request`, `pull_request_review`, `push` events at
  minimum.

Install the app on a test repo. Open a PR — the dashboard should light up
within a few seconds (Socket.IO push) with a scored PR row.

---

## 5 · What to watch on free tier

- **Spin-down**: free web services sleep after 15 minutes of no traffic. When
  the api sleeps, Socket.IO drops; the first request after a sleep takes
  ~30s. `meridian-ml` is also a free web service (not private — free tier
  doesn't offer that), so it sleeps too and the first scoring request after
  idle will be slow. The api's `scorePR` already falls back to a rule-only
  score if the ml call fails or times out, so webhook ingestion doesn't
  stall.
- **DB retention**: free Postgres expires after 90 days and is deleted. Move
  to a paid plan before you care about the data.
- **Region locking**: keep all four resources in the same region so the
  api→ml round-trip stays on Render's backbone rather than the public
  internet.

---

## 6 · Custom domains (optional)

If you want `app.yourcompany.com` instead of the `.onrender.com` URLs:

1. Add a custom domain on `meridian-web` and `meridian-api` in the Render
   dashboard. Follow the DNS instructions Render gives you.
2. Update `WEB_ORIGIN`, `ALLOWED_ORIGINS`, `VITE_API_BASE`, and
   `GITHUB_OAUTH_CALLBACK` to the new hostnames.
3. If both hostnames share an apex (e.g. `app.co` and `api.app.co`), set
   `COOKIE_DOMAIN=.app.co` on the api so the auth cookie is valid on both.
   If they don't share an apex, leave `COOKIE_DOMAIN` blank and stick with
   the default host-only cookie.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Web loads but every API call is CORS-blocked | `ALLOWED_ORIGINS` on api doesn't include the exact web origin (scheme + host, no path) |
| GitHub sign-in button 503s | GitHub App creds not set on api — this is intentional (no silent fallback). Set them or ignore. |
| `/health/ready` returns `db_unreachable` | `DATABASE_URL` binding broken, or DB is still provisioning. Redeploy api after the DB shows "Available." |
| Socket.IO won't connect in prod | `VITE_API_BASE` wasn't set at web build time. Change it in the web service env and trigger a rebuild. |
| Webhook returns 401 | `GITHUB_WEBHOOK_SECRET` in the api env doesn't match the value in your GitHub App's webhook config. |
| ML service returns 503 on first call after idle | Free tier cold start. Upgrade `meridian-ml` to Starter to keep it warm. |
